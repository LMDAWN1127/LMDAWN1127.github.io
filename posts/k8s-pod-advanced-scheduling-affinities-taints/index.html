一、Pod 调度#

1.1 nodeName——绕过调度器#

1
2
3
4
5
6

# 直接指定节点，调度器完全不参与
spec:
  nodeName: worker01
  containers:
  - name: c1
    image: harbor:443/dawn/apps:v2

危险： 绕过调度器的全部保护（资源检查、Pod 上限、污点容忍），副本控制器 + nodeName 的组合尤其容易引发 Pod 风暴（见后）

    ports:

二、污点（Taints）#

污点作用于节点，语法：key[=value]:effect。

2.1 三种 effect#

effect新 Pod 调度已有 Pod删除命令
NoSchedule禁止受影响kubectl taint node N key-
PreferNoSchedule尽量避开不受影响kubectl taint node N key=val:PreferNoSchedule-
NoExecute禁止立刻驱逐kubectl taint node N key=val:NoExecute-

# /dawn/manifests/scheduler/10-scheduler-nodeAffinity.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: scheduler-nodeaffinity
spec:
  selector:
    matchLabels:
      apps: xiuxian
  template:
    spec:
      tolerations:
      - key: node-role.kubernetes.io/master
        effect: NoSchedule
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: school
                values:
                - "dawn"
                operator: In                # In / NotIn / Exists / DoesNotExist / Gt / Lt
      containers:
      - name: xiuxian
        image: harbor:443/dawn/apps:v1

六、nodeAffinity 软限制 —— preferredDuringSchedulingIgnoredDuringExecution#

6.1 硬限制 vs 软限制#

硬限制 (required)软限制 (preferred)
条件不满足 → Pod 永远 Pending条件不满足 → fallback 到其他节点
nodeSelector 也属于硬限制只有 nodeAffinity 支持
适合必须满足的场景（GPU/数据本地性）适合"最好这样但不强制"

结论： weight=40 的 dark 吸引最多 Pod；yitiantian 虽不在任何偏好列表中，仍可调度（软限制 fallback）。生产环境中正向用例：优先同 AZ 部署，跨 AZ 做 fallback。

7.1 原理#

八、podAntiAffinity —— Pod 反亲和性（跨拓扑域打散）#

8.1 原理#

podAntiAffinity 是 podAffinity 的反面：不要和含特定标签的 Pod 在同一拓扑域。经典场景：高可用部署——同一应用不要全堆在一台机器 / 一个机架 / 一个可用区。

逐步分析：
