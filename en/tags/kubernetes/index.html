K8S Pod Port Exposure and SVC Multi-Port Mapping in Practice: hostPort, Multi-Port Mapping and targetPort Name Matching

This article covers two things in K8S: exposing Pod ports and mapping multiple ports on a SVC. The first half uses hostPort to map container port 80 straight to 8888 on the node hosting the Pod, so external traffic reaches the container without going through a SVC; the access test from Windows succeeds, and hostPort is compared against NodePort (hostPort only works on the Pod’s node and its address follows the Pod when it moves, while NodePort is a Service that opens the same port on every node so movement does not affect access). The second half writes a Pod exposing both 80/TCP and 53/UDP, maps both through a SVC, inspects the PORT(S) column and the describe TargetPort/Endpoints, and finally patches targetPort to match by port name, verifying that the SVC keeps tracking the endpoint as long as the name is unchanged even if the container port number changes.

K8S Namespace Management in Practice: Imperative and Declarative Management, Cross-Namespace Service Access

This article walks through K8S namespace management. It starts with what namespaces do and how to tell namespaced from cluster-scoped resources (the NAMESPACED column of kubectl api-resources). Then it creates, lists, labels and deletes namespaces with imperative commands, and creates a Pod named xiuxian-v1 in both default and dawn to demonstrate isolation and the cascade delete that happens when a namespace is removed. Next it switches to declarative management: export a YAML from an existing resource and subtract from it, then apply to create a labeled namespace. Finally it puts MySQL in dawn and WordPress in kube-public, connects them using the cross-namespace short form db-svc.dawn, and lists the three ways to write a cross-namespace A record with the measured results.

K8S Pod DNS Policy and hostNetwork in Practice: A dnsPolicy Comparison

This article uses a control experiment to explain how a K8S Pod’s dnsPolicy interacts with hostNetwork. The test Pod sets hostNetwork: true and explicitly sets dnsPolicy: ClusterFirstWithHostNet; inside the container /etc/resolv.conf points at the cluster CoreDNS and carries the svc search domains, so db-svc, kubernetes and kube-dns all resolve. The control Pod only enables hostNetwork and leaves dnsPolicy at its ClusterFirst default; resolv.conf becomes the node’s own DNS with no search domains, and db-svc fails to resolve outright. Conclusion: once a Pod uses the host network, you must set dnsPolicy to ClusterFirstWithHostNet.

K8S in Practice: WordPress Deployment, NFS Persistence and CoreDNS Name Resolution

This article deploys WordPress on a K8S cluster and evolves it through three versions. v1 gets the basic chain working with ReplicationControllers and Services: MySQL RC to SVC ClusterIP with a pinned VIP, to WordPress RC, to SVC NodePort, finishing the installer in a browser; scaling WordPress to 3 replicas then exposes the data inconsistency caused by the lack of persistence. v2 introduces NFS shared storage so both MySQL data and the WordPress uploads directory land on NFS — after deleting the RC and letting it rebuild 3 fresh Pods, the marker files are still there, proving all replicas share the same data. v3 deploys the CoreDNS add-on so WordPress reaches the database by SVC name, and validates cluster DNS resolution three ways: from the manifests, by pinging SVC names inside a Pod, and with dig A-record lookups.
